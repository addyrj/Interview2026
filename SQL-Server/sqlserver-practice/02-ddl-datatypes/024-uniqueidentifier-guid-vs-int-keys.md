# Q024. UNIQUEIDENTIFIER (GUID) vs INT Keys
# Category: DDL + DATA TYPES
# Difficulty: ⭐⭐⭐ Hard
# DB: SQL Server (MySQL: UUID() / BINARY(16); PostgreSQL: native uuid type, gen_random_uuid())

---

## ❓ Question
Should the Customers primary key be `INT IDENTITY` or `UNIQUEIDENTIFIER`? Explain NEWID() vs NEWSEQUENTIALID(), page splits on a clustered GUID key, the extra index size, and a design that gets the best of both (INT clustered key plus a GUID public id).
 
---

## 💡 Quick Concept (2 lines only)
A GUID is 16 bytes (4 for INT). `NEWID()` is random, so inserts land all over a clustered index causing page splits and fragmentation; `NEWSEQUENTIALID()` (DEFAULT only) is increasing per server restart window and fragments much less.
हिंदी: GUID 16 byte है, INT 4 byte। NEWID() random है, इसलिए clustered index में page splits होते हैं। Public id के लिए GUID, clustered key INT रखना अक्सर बेहतर।

---

## ✅ Answer / Solution

```sql
-- ============================================
-- SETUP: INT clustered key + GUID as a public (external) identifier
-- ============================================

CREATE TABLE Customers (
  CustomerId INT IDENTITY(1,1) NOT NULL,
  PublicId   UNIQUEIDENTIFIER NOT NULL
             CONSTRAINT DF_Customers_PublicId DEFAULT NEWSEQUENTIALID(),
  Name       NVARCHAR(100) NOT NULL,
  CONSTRAINT PK_Customers PRIMARY KEY CLUSTERED (CustomerId),
  CONSTRAINT UQ_Customers_PublicId UNIQUE NONCLUSTERED (PublicId)
);

INSERT INTO Customers (PublicId, Name) VALUES
  ('6F9619FF-8B86-D011-B42D-00C04FC964FF', N'Asha'),
  ('0E984725-C51C-4BF4-9960-E1C80E27ABA0', N'Ravi');
GO

-- ============================================
-- SOLUTION: look up by the public GUID, join internally on INT
-- ============================================

SELECT CustomerId, Name
FROM Customers
WHERE PublicId = '0E984725-C51C-4BF4-9960-E1C80E27ABA0';

-- Output:
-- CustomerId | Name
-- 2          | Ravi

-- Result derived from an equivalent lookup on SQLite 3.49 (GUID stored as text); not executed on SQL
-- Server. Fragmentation/size claims are per Microsoft docs, not measured here.

-- Generating values (outputs are random, so none shown)
SELECT NEWID() AS RandomGuid;                 -- random, usable anywhere (also in the app)
-- NEWSEQUENTIALID() is allowed ONLY in a DEFAULT constraint, not in a SELECT or the application.

-- Sizes
SELECT DATALENGTH(CAST(1 AS INT)) AS IntBytes, DATALENGTH(NEWID()) AS GuidBytes;
-- Output per Microsoft docs: IntBytes = 4, GuidBytes = 16 (not executed on SQL Server)
```

---

## 🔍 Why This Works (3 lines max)
The clustered key is copied into every non-clustered index, so a 16-byte key makes every index larger than a 4-byte one, and random GUIDs insert into random pages (page splits, low page density). Keeping the clustered key narrow, ever-increasing and unique (INT IDENTITY) while exposing a GUID externally prevents enumeration of ids (`/customers/1`, `/customers/2`) without paying the clustering cost.
हिंदी: Clustered key हर non-clustered index में copy होती है, इसलिए narrow रखो। GUID को unique non-clustered column बनाकर बाहर expose करो ताकि id guess न हो।

## ⚡ Alternative Solution

```sql
-- GUID as the clustered key is acceptable when ids are generated by many clients/services
-- (merge replication, offline apps, microservices) - mitigate with NEWSEQUENTIALID()
CREATE TABLE Orders (
  OrderId    UNIQUEIDENTIFIER NOT NULL CONSTRAINT DF_Orders_Id DEFAULT NEWSEQUENTIALID(),
  CustomerId INT NOT NULL,
  CONSTRAINT PK_Orders PRIMARY KEY CLUSTERED (OrderId)
);

-- Cluster on something sequential, keep the GUID PK non-clustered:
CREATE TABLE Events (
  EventSeq BIGINT IDENTITY NOT NULL,
  EventId  UNIQUEIDENTIFIER NOT NULL DEFAULT NEWID(),
  CONSTRAINT PK_Events PRIMARY KEY NONCLUSTERED (EventId)
);
CREATE UNIQUE CLUSTERED INDEX CX_Events ON Events (EventSeq);

-- Application-side sequential GUIDs (e.g., UUIDv7 or COMB) are another option for client-generated ids.
```

## ⚠️ Common Mistake

```sql
-- ❌ Wrong: random NEWID() as CLUSTERED primary key on a high-insert table
CREATE TABLE Payments (
  PaymentId UNIQUEIDENTIFIER NOT NULL DEFAULT NEWID() PRIMARY KEY,   -- PRIMARY KEY is clustered by default!
  Amount    DECIMAL(12,2) NOT NULL
);
-- Expect heavy fragmentation, bigger indexes and more log/IO.

-- ❌ Wrong: storing GUIDs as VARCHAR(36) - 36+ bytes and slower compares
-- ❌ Wrong: using NEWSEQUENTIALID() in a SELECT or from the app (not allowed; only DEFAULT)
-- ❌ Wrong: assuming sequential GUID order is stable forever - it can restart lower after a server
--           restart, and it sorts by SQL Server's GUID comparison (last bytes first), not by string
```

---

## 🎯 Interview Tip (1 line)
Say: "Default to INT/BIGINT IDENTITY as the clustered key and add a UNIQUEIDENTIFIER (or other opaque id) as a public key if I must hide sequence or generate ids outside the database. If GUID must be the clustered key, I use NEWSEQUENTIALID and watch fragmentation." Mention Node.js: the `mssql` driver returns uniqueidentifier values as strings (compare case-insensitively in JS).
