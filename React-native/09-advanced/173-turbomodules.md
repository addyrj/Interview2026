# 173. TurboModules
# हिंदी में: TurboModules (नए, तेज़ Native Modules)
# Platform: Android ✅ | iOS ✅ | Both ✅

> **Expo SDK 54 (React Native 0.81) target** — check current docs — APIs change between SDKs. TurboModules need the New Architecture; spec file names must start with `Native` for Codegen conventions.

---

## 🔵 Simple Definition (English)
A **TurboModule** is a native module (Kotlin/Java, Objective-C/Swift, or C++) that JS calls through **JSI** instead of the old bridge. It is **lazy-loaded** (created on first use) and described by a **typed spec** that **Codegen** turns into native interfaces.

## 🔵 सरल परिभाषा (Hindi)
**TurboModule** एक native module है (Kotlin/Java, Objective-C/Swift या C++) जिसे JS पुराने bridge की जगह **JSI** से call करता है। यह **lazy-load** होता है (पहली बार use पर बनता है) और एक **typed spec** से बताया जाता है जिसे **Codegen** native interfaces में बदल देता है।

---

## 🔴 Problem it Solves
```
OLD NativeModules:
❌ All modules initialized at app start (even unused: Bluetooth, NFC...)
❌ Calls = JSON serialization + async only
❌ Method signature mismatch found only at runtime (crash)
❌ No synchronous methods without hacks
```

## 🔴 यह क्यों बना? (Hindi)
```
पुराने NativeModules:
❌ App start पर सारे modules initialize (Bluetooth, NFC जो use नहीं हुए वे भी)
❌ Calls = JSON serialization + सिर्फ async
❌ Signature mismatch runtime पर पता चलता था (crash)
❌ बिना hack के synchronous methods नहीं
```

## 🟢 How it Works — Step by Step
```
Step 1 → Write a TypeScript spec: NativeXxx.ts extends TurboModule
Step 2 → Add codegenConfig in package.json (name, type, jsSrcsDir)
Step 3 → Build: Codegen creates native interfaces (ObjC++/Java + C++)
Step 4 → Implement the interface in Kotlin/Java and Objective-C++/Swift
Step 5 → JS: TurboModuleRegistry.getEnforcing<Spec>('Name')
Step 6 → First call: module is created lazily, JSI host object returned
Step 7 → Methods run direct; sync methods return values immediately
```

## 🟢 कैसे काम करता है? (Hindi)
```
Step 1 → TypeScript spec लिखो: NativeXxx.ts जो TurboModule extend करे
Step 2 → package.json में codegenConfig जोड़ो (name, type, jsSrcsDir)
Step 3 → Build पर Codegen native interfaces बनाता है (ObjC++/Java + C++)
Step 4 → Kotlin/Java और Objective-C++/Swift में interface implement करो
Step 5 → JS में: TurboModuleRegistry.getEnforcing<Spec>('Name')
Step 6 → पहली call पर module lazily बनता है
Step 7 → Methods सीधे चलते हैं; sync methods तुरंत value लौटाते हैं
```

**Paytm/PhonePe** style app: a `NativeDeviceSecurity` TurboModule checks root/jailbreak and returns a result synchronously at login. **Zomato** could expose `NativeLocationCache`. Because modules are lazy, the "KYC scanner" module is not created until the user opens KYC — faster app start.

## 💻 Code Example — Basic
```ts
// NativeDeviceInfoModule.ts  — the TurboModule SPEC (TypeScript)
// File must be in jsSrcsDir configured in package.json "codegenConfig"
import type { TurboModule } from 'react-native'; // base interface
import { TurboModuleRegistry } from 'react-native'; // registry to fetch the module

// Spec: every method here becomes a native method signature via Codegen
export interface Spec extends TurboModule {
  // synchronous method: returns string immediately
  getDeviceName(): string;
  // async method: returns a Promise (maps to promise in native)
  getBatteryLevel(): Promise<number>;
  // method with parameter
  logEvent(name: string, value: number): void;
}

// getEnforcing throws if the native module is missing (fail fast)
export default TurboModuleRegistry.getEnforcing<Spec>('DeviceInfoModule');
```
```json
{
  "name": "my-device-info",
  "version": "0.0.1",
  "codegenConfig": {
    "name": "DeviceInfoSpec",
    "type": "modules",
    "jsSrcsDir": "src",
    "android": { "javaPackageName": "com.deviceinfo" }
  }
}
```

## 💻 Code Example — Advanced
```kotlin
// Android implementation (Kotlin) of the generated spec
// NativeDeviceInfoModuleSpec is generated by Codegen from the TS spec
package com.deviceinfo

import android.os.BatteryManager            // Android battery API
import android.os.Build                      // device model info
import android.content.Context              // app context
import com.facebook.react.bridge.Promise    // JS Promise bridge
import com.facebook.react.bridge.ReactApplicationContext // RN context
import com.facebook.react.module.annotations.ReactModule // registers the module name

@ReactModule(name = DeviceInfoModule.NAME)  // name must match JS 'DeviceInfoModule'
class DeviceInfoModule(reactContext: ReactApplicationContext) :
    NativeDeviceInfoModuleSpec(reactContext) { // generated abstract class

  override fun getName() = NAME             // module name

  // sync method (returns String directly)
  override fun getDeviceName(): String = Build.MODEL // e.g. "Pixel 8"

  // async method resolves a Promise with a number
  override fun getBatteryLevel(promise: Promise) {
    try {
      val bm = reactApplicationContext.getSystemService(Context.BATTERY_SERVICE) as BatteryManager
      val level = bm.getIntProperty(BatteryManager.BATTERY_PROPERTY_CAPACITY) // 0..100
      promise.resolve(level.toDouble())     // JS number == double
    } catch (e: Exception) {
      promise.reject("E_BATTERY", e)        // error handling -> JS catch
    }
  }

  override fun logEvent(name: String, value: Double) {
    android.util.Log.d("DeviceInfo", "$name=$value") // simple logging
  }

  companion object { const val NAME = "DeviceInfoModule" } // constant name
}
```
```jsx
// JS usage with error handling (works on Android; iOS needs the matching ObjC++/Swift implementation)
import React, { useEffect, useState } from 'react';
import { Text, View, Platform } from 'react-native';
import DeviceInfo from './NativeDeviceInfoModule'; // the spec file's default export

export default function Battery() {
  const [level, setLevel] = useState(null);      // battery %
  useEffect(() => {
    DeviceInfo.getBatteryLevel()                  // async native call
      .then(setLevel)                             // store result
      .catch((e) => console.warn('battery failed', e)); // handle reject
  }, []);
  return <View style={{ marginTop: 80 }}><Text>{Platform.OS} {DeviceInfo.getDeviceName()} - {level ?? '...'}%</Text></View>;
}
```

## 📱 Android vs iOS Difference
| Feature | Android | iOS |
|---------|---------|-----|
| Implementation language | Kotlin / Java | Objective-C++ (or Swift via a wrapper) |
| Spec base class | `NativeXxxSpec` (generated Java abstract class) | `NativeXxxSpec` protocol (generated) |
| Registration | `@ReactModule` + `TurboReactPackage`/`BaseReactPackage` | Module class name matched via `RCT_EXPORT_MODULE` / `getTurboModule:` |
| Threading | Methods on native modules thread unless sync | Methods on module's method queue |
| Permissions | AndroidManifest | Info.plist |

## 🟠 Expo vs CLI Difference
Expo way:
```bash
# Prefer Expo Modules API for new modules (simpler than writing TurboModule glue)
npx create-expo-module@latest my-device-info
# Works in prebuild/dev client; not in Expo Go (custom native code)
npx expo run:android
```
CLI way:
```bash
# Library with codegen: use create-react-native-library
npx create-react-native-library@latest my-device-info   # choose "Turbo module"
# then build the app: Codegen runs automatically during Gradle / pod install
cd ios && bundle exec pod install
```

## ⚠️ Common Mistakes to Avoid
❌ Mistake 1: Spec file not named `Native*.ts` or missing from `jsSrcsDir`
✅ Correct: Name it `NativeXxx.ts` inside the configured folder, otherwise Codegen skips it.

❌ Mistake 2: Using unsupported types (e.g., `any`, unions of arbitrary objects)
✅ Correct: Use supported types: `string`, `number`, `boolean`, `Object`, arrays, `Promise<T>`, typed objects.

❌ Mistake 3: Expecting it to run in Expo Go
✅ Correct: Custom native code needs a development build.

## 🧠 Tricky Interview Question
**Q: Your TurboModule spec declares `getName(): string`. In JS it returns instantly, but the native code needs 200 ms (disk read). What should you change?**

**Answer:** Do not keep it synchronous: sync calls block the JS thread. Change it to `getName(): Promise<string>` and do the work on a background thread in native. Use sync methods only for tiny, fast reads.

## ⚫ Interview Questions + Answers

**Q1: How are TurboModules different from NativeModules?**
A1: Lazy loaded, call via JSI (no JSON bridge), typed by Codegen specs, and can have sync methods.

**Q2: What is `TurboModuleRegistry.getEnforcing`?**
A2: Returns the module or throws if missing. `get` returns `null` instead.

**Q3: Where does the spec live?**
A3: In a TypeScript/Flow file, `NativeXxx.ts`, in the folder from `codegenConfig.jsSrcsDir`.

**Q4: When are they created?**
A4: On first access from JS.

**Q5: Can you still use old native modules?**
A5: Many work through the interop layer, but new code should use TurboModules or the Expo Modules API.

---

## 🔷 When to Use + When Not to Use
✅ Use when:
- You need platform APIs not available in RN/Expo
- Performance-sensitive calls or sync reads
- Library authors supporting New Architecture

❌ Avoid when:
- An Expo/community package already does the job
- You are using Expo Go only (no custom native code)
