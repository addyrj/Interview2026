# Q029. SERIAL vs IDENTITY vs AUTO_INCREMENT
# Category: Data Types & DDL
# Difficulty: ⭐⭐ Medium
# DB: Both (MySQL AUTO_INCREMENT | PostgreSQL SERIAL / IDENTITY)

---

## ❓ Question
How do you auto-generate surrogate keys in MySQL (AUTO_INCREMENT) and PostgreSQL (SERIAL vs GENERATED AS IDENTITY)? What are the differences, the gap behaviour, and which should you use in PostgreSQL today?

---

## 💡 Quick Concept (2 lines only)
MySQL AUTO_INCREMENT is a column attribute; PostgreSQL SERIAL is shorthand for "create a sequence + DEFAULT nextval()", while `GENERATED {ALWAYS | BY DEFAULT} AS IDENTITY` (SQL standard, PG 10+) ties the sequence to the column properly. In all of them ids are unique and increasing, but not gap-free.
हिंदी: AUTO_INCREMENT MySQL का है; PgSQL में नया और सही तरीका IDENTITY है, SERIAL पुराना shortcut है; gaps normal हैं।

---

## ✅ Answer / Solution

```sql
-- ============================================
-- SETUP (MySQL) — run this first
-- ============================================

CREATE TABLE invoices (
  id     INT AUTO_INCREMENT PRIMARY KEY,
  number VARCHAR(20) UNIQUE,
  amount DECIMAL(10,2)
);

-- ============================================
-- SOLUTION (MySQL 9.1.0, verified)
-- ============================================

INSERT INTO invoices (number, amount) VALUES ('INV-1', 100), ('INV-2', 200);
SELECT LAST_INSERT_ID() AS last_id;
-- last_id = 1                 <- multi-row insert: returns the FIRST generated id

-- A FAILED insert still consumes an id => gap
INSERT INTO invoices (number, amount) VALUES ('INV-1', 999);
-- ERROR 1062 (23000): Duplicate entry 'INV-1' for key 'invoices.number'
INSERT INTO invoices (number, amount) VALUES ('INV-3', 300);
SELECT id, number FROM invoices ORDER BY id;
-- id | number
-- 1  | INV-1
-- 2  | INV-2
-- 4  | INV-3                  <- id 3 was burned by the failed insert (innodb_autoinc_lock_mode = 2)

-- Manual id bumps the counter forward
INSERT INTO invoices (id, number, amount) VALUES (100, 'INV-100', 1);
INSERT INTO invoices (number, amount) VALUES ('INV-101', 2);
SELECT id, number FROM invoices ORDER BY id;
-- 1 INV-1 | 2 INV-2 | 4 INV-3 | 100 INV-100 | 101 INV-101

-- Deleting the newest rows does NOT roll the counter back
DELETE FROM invoices WHERE id >= 100;
INSERT INTO invoices (number, amount) VALUES ('INV-AFTER-DELETE', 5);
SELECT MAX(id) AS max_id FROM invoices;
-- max_id = 102
SELECT AUTO_INCREMENT FROM information_schema.tables WHERE table_schema = DATABASE() AND table_name = 'invoices';
-- 103   (MySQL 8+ persists the counter across restarts; 5.7 recomputed MAX(id)+1 and could reuse ids)

-- ============================================
-- PostgreSQL version (verified on PostgreSQL 18 via PGlite)
-- ============================================
CREATE TABLE invoices_serial   (id SERIAL PRIMARY KEY, number VARCHAR(20) UNIQUE, amount NUMERIC(10,2));
CREATE TABLE invoices_identity (id INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY, number VARCHAR(20) UNIQUE, amount NUMERIC(10,2));
CREATE TABLE invoices_by_default (id INT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY, number VARCHAR(20) UNIQUE, amount NUMERIC(10,2));

INSERT INTO invoices_serial (number, amount) VALUES ('INV-1',100),('INV-2',200);
INSERT INTO invoices_serial (number, amount) VALUES ('INV-1',999);        -- ERROR: duplicate key value violates unique constraint "invoices_serial_number_key"
INSERT INTO invoices_serial (number, amount) VALUES ('INV-3',300) RETURNING id;
-- id = 4                                    <- gap again: sequences are non-transactional

-- Manual id does NOT move the sequence => later collision
INSERT INTO invoices_serial (id, number, amount) VALUES (50,'INV-50',1);   -- OK, sequence still at 4
-- ...four more normal inserts (INV-X..W) take ids 5,6,7,8; the sequence would hit 50 later => pkey violation

-- GENERATED ALWAYS blocks manual ids unless you explicitly override
INSERT INTO invoices_identity (number, amount) VALUES ('INV-1',100) RETURNING id;      -- 1
INSERT INTO invoices_identity (id, number, amount) VALUES (7,'INV-7',1);
-- ERROR: cannot insert a non-DEFAULT value into column "id"
INSERT INTO invoices_identity (id, number, amount) OVERRIDING SYSTEM VALUE VALUES (7,'INV-7',1) RETURNING id;   -- 7

-- BY DEFAULT identity has the same trap as SERIAL if you mix manual and automatic ids
INSERT INTO invoices_by_default (id, number, amount) VALUES (1,'INV-1',1);
INSERT INTO invoices_by_default (number, amount) VALUES ('INV-2',1);
-- ERROR: duplicate key value violates unique constraint "invoices_by_default_pkey"   (sequence also gave 1)

-- Introspection
SELECT pg_get_serial_sequence('invoices_serial','id')   AS serial_seq,
       pg_get_serial_sequence('invoices_identity','id') AS identity_seq;
-- public.invoices_serial_id_seq | public.invoices_identity_id_seq
SELECT column_default FROM information_schema.columns WHERE table_name='invoices_serial' AND column_name='id';
-- nextval('invoices_serial_id_seq'::regclass)          <- SERIAL = plain DEFAULT
SELECT is_identity, identity_generation FROM information_schema.columns WHERE table_name='invoices_identity' AND column_name='id';
-- YES | ALWAYS

-- Restart / resync
ALTER TABLE invoices_identity ALTER COLUMN id RESTART WITH 1000;
INSERT INTO invoices_identity (number, amount) VALUES ('INV-1000',1) RETURNING id;     -- 1000
SELECT setval(pg_get_serial_sequence('invoices_serial','id'), (SELECT MAX(id) FROM invoices_serial));   -- 50
INSERT INTO invoices_serial (number, amount) VALUES ('INV-NEXT',1) RETURNING id;       -- 51

-- ============================================
-- EXPECTED OUTPUT
-- ============================================
-- All values above copied from the real runs (MySQL 9.1.0 / PostgreSQL 18 via PGlite).
```

## 🔍 Why This Works (3 lines max)
All three pull the next value from a counter that is deliberately outside transaction rollback (so concurrent inserts never block each other) — hence gaps after failures or rollbacks. IDENTITY differs from SERIAL by being a real column property (owned sequence, dropped with the table, permission-simple, `ALWAYS` guards against manual ids).
हिंदी: Counter transaction से बाहर रहता है इसलिए rollback पर भी id जल जाती है; IDENTITY sequence को column से सही जोड़ता है।

## ⚡ Alternative Solution

```sql
-- Comparison
--                         MySQL AUTO_INCREMENT | PG SERIAL           | PG IDENTITY
-- standard SQL ........... no                  | no                  | yes (SQL:2003)
-- backing object ........ table counter        | separate sequence   | owned internal sequence
-- block manual ids ....... no                  | no                  | ALWAYS (use OVERRIDING SYSTEM VALUE)
-- grants .................. table privilege     | need sequence USAGE | covered by table INSERT
-- copy table (LIKE) ...... -                    | shares/copies default| LIKE ... INCLUDING IDENTITY
-- last generated id ...... LAST_INSERT_ID()     | RETURNING / currval | RETURNING / currval

-- Wider types: BIGSERIAL / SMALLSERIAL, or BIGINT GENERATED ALWAYS AS IDENTITY (preferred for big tables, see Q021)
CREATE TABLE events (id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY, name TEXT);

-- Tune generator
CREATE TABLE tickets (id INT GENERATED BY DEFAULT AS IDENTITY (START WITH 1000 INCREMENT BY 10) PRIMARY KEY);

-- MySQL multi-source offsets (replication/Galera): auto_increment_increment = 2, auto_increment_offset = 1
-- Gap-free numbering (legal invoice numbers) cannot use any of these: use a counter row locked with
-- SELECT ... FOR UPDATE inside the same transaction (see Q017) — it serialises writers.
```

## ⚠️ Common Mistake

```sql
-- ❌ Wrong: assuming ids are gap-free or that MAX(id) = row count — rollbacks, failed inserts and deletes leave holes
-- ❌ Wrong: ordering by id as a proxy for "creation time" across concurrent transactions
--          (commit order can differ from id order)
-- ❌ Wrong (PgSQL): bulk-loading rows with explicit ids into a SERIAL / BY DEFAULT table and not resetting the sequence
SELECT setval(pg_get_serial_sequence('invoices_serial','id'), (SELECT MAX(id) FROM invoices_serial));   -- ✅ fix
-- ❌ Wrong: INT AUTO_INCREMENT on hot tables (overflow => ERROR 1062 duplicate; see Q021)
-- ❌ Wrong (PgSQL): new code using SERIAL when IDENTITY is available

-- ✅ Correct: BIGINT GENERATED ALWAYS AS IDENTITY (PgSQL) / BIGINT UNSIGNED AUTO_INCREMENT (MySQL)
```

---

## 🎯 Interview Tip (1 line)
Say: "In PostgreSQL I use GENERATED ALWAYS AS IDENTITY on BIGINT instead of SERIAL because it's standard, owns its sequence and prevents accidental manual ids; I never rely on gap-free or commit-ordered ids — those need a locked counter table."
