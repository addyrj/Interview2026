# 117. JWT (JSON Web Token)
# हिंदी में: JWT — Stateless Authentication Token

---

## 🔵 Simple Definition (English)
**JWT (JSON Web Token)** is a compact, self-contained token for securely transmitting claims between client and server. It's a Base64URL-encoded string with 3 parts separated by dots: `header.payload.signature`. The server generates JWT on login; client sends it with every request in the `Authorization: Bearer <token>` header; server verifies the signature WITHOUT needing a database lookup — making it stateless. Used for authentication (who you are) and authorization (what you can do).

## 🔵 सरल परिभाषा (Hindi)
**JWT** एक compact, self-contained token है जो client और server के बीच claims securely transmit करता है। 3 parts (Base64URL encoded) dot से separated: `header.payload.signature`। Server login पर JWT generate करता है; client हर request में `Authorization: Bearer <token>` header में भेजता है; server signature verify करता है **database lookup के बिना** — stateless authentication। Use: authentication (तुम कौन हो) + authorization (तुम क्या कर सकते हो)।

## 🔴 Problem it Solves
```
TRADITIONAL SESSION-BASED AUTH (with problems):
  Login → Server creates session in DB → Returns session_id cookie
  
  Every request:
    Client sends session_id cookie
    Server looks up session_id in DB → 1 DB query per request
    Server finds session → allows request
    
  Problems:
    1. Every request = DB lookup (latency)
    2. Sessions stored in DB = state on server
    3. Multiple servers: server2 doesn't have server1's sessions
       (need sticky sessions or shared Redis)
    4. Mobile apps: cookies are not ideal
    5. Microservices: which service has the sessions?

JWT SOLUTION:
  Login → Server generates JWT with user info → Returns JWT (no DB storage)
  
  Every request:
    Client sends JWT in Authorization header
    Server verifies SIGNATURE (crypto math, no DB!)
    Valid signature? → Trust the payload, allow request
    
  Benefits:
    1. No DB lookup = faster
    2. Stateless = any server can verify (horizontal scaling)
    3. Works for mobile, SPAs, microservices
    4. Self-contained: payload has user info (id, role, email)
```

## 🟢 JWT Structure

```
JWT TOKEN:
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJ1c2VySWQiOiIxMjMiLCJlbWFpbCI6InJhaHVsQGV4YW1wbGUuY29tIiwicm9sZSI6InVzZXIiLCJpYXQiOjE3MDUzMTIwMDAsImV4cCI6MTcwNTMxNTYwMH0.SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c

PART 1 — HEADER (Base64URL decoded):
{
  "alg": "HS256",  // algorithm: HMAC-SHA256
  "typ": "JWT"
}

PART 2 — PAYLOAD (Base64URL decoded):
{
  "userId": "123",
  "email": "rahul@example.com",
  "role": "user",
  "iat": 1705312000,  // issued at (Unix timestamp)
  "exp": 1705315600   // expires at (1 hour later)
}

PART 3 — SIGNATURE:
HMAC_SHA256(
  Base64URL(header) + "." + Base64URL(payload),
  SECRET_KEY
)

HOW VERIFICATION WORKS:
  Server receives: header.payload.signature
  Server recomputes: HMAC_SHA256(header + "." + payload, SECRET_KEY)
  
  If recomputed == received signature → payload not tampered ✅
  If recomputed != received signature → payload was modified ❌
  
  IMPORTANT: Payload is NOT encrypted — anyone can Base64 decode it!
  It's only SIGNED (tamper-proof), not secret.
  Never put passwords or sensitive data in JWT payload.
```

## 🟡 Real World Example
**Paytm UPI app:** User logs in with PIN → Server generates Access Token (15 min expiry) + Refresh Token (30 days, stored in HttpOnly cookie). App stores Access Token in memory. Every API call sends `Authorization: Bearer <access_token>`. Payment service, order service, wallet service — all can verify JWT with same SECRET_KEY without calling auth service. When Access Token expires (15 min), app uses Refresh Token to get new Access Token silently. User never logs in again for 30 days unless Refresh Token expires.

## 💻 Code Example — Basic

```javascript
// jwt-basics.js
const jwt = require('jsonwebtoken');  // npm install jsonwebtoken

const JWT_SECRET = process.env.JWT_SECRET;          // from .env
const JWT_REFRESH_SECRET = process.env.JWT_REFRESH_SECRET;  // different secret!

// ─── 1. GENERATE TOKENS ───────────────────────────────────────────────────────
function generateTokens(user) {
  const payload = {
    userId: user._id.toString(),
    email: user.email,
    role: user.role,  // 'user' | 'admin' | 'vendor'
  };

  const accessToken = jwt.sign(
    payload,
    JWT_SECRET,
    {
      expiresIn: '15m',  // short-lived: 15 minutes
      issuer: 'myapp.com',
      audience: 'myapp-users',
    }
  );

  const refreshToken = jwt.sign(
    { userId: user._id.toString() },  // minimal payload
    JWT_REFRESH_SECRET,               // DIFFERENT secret
    {
      expiresIn: '30d',  // long-lived: 30 days
    }
  );

  return { accessToken, refreshToken };
}

// ─── 2. VERIFY TOKEN ──────────────────────────────────────────────────────────
function verifyAccessToken(token) {
  try {
    const decoded = jwt.verify(token, JWT_SECRET, {
      issuer: 'myapp.com',
      audience: 'myapp-users',
    });
    return { valid: true, payload: decoded };
  } catch (err) {
    if (err.name === 'TokenExpiredError') {
      return { valid: false, expired: true, error: 'Token expired' };
    }
    if (err.name === 'JsonWebTokenError') {
      return { valid: false, expired: false, error: 'Invalid token' };
    }
    return { valid: false, error: err.message };
  }
}

// ─── 3. USAGE IN EXPRESS ──────────────────────────────────────────────────────
const express = require('express');
const bcrypt = require('bcrypt');
const app = express();
app.use(express.json());

// POST /auth/login
app.post('/auth/login', async (req, res) => {
  const { email, password } = req.body;

  // Validate input
  if (!email || !password) {
    return res.status(400).json({ error: 'Email and password required' });
  }

  try {
    // Find user in DB
    const user = await User.findOne({ email });
    if (!user) {
      return res.status(401).json({ error: 'Invalid credentials' });
      // Don't say "user not found" — attacker learns email existence
    }

    // Verify password
    const passwordMatch = await bcrypt.compare(password, user.passwordHash);
    if (!passwordMatch) {
      return res.status(401).json({ error: 'Invalid credentials' });
    }

    // Generate tokens
    const { accessToken, refreshToken } = generateTokens(user);

    // Store refresh token in DB (to enable logout/revocation)
    await User.findByIdAndUpdate(user._id, {
      $push: { refreshTokens: { token: refreshToken, createdAt: new Date() } },
    });

    // Send refresh token as HttpOnly cookie (can't be accessed by JS)
    res.cookie('refreshToken', refreshToken, {
      httpOnly: true,
      secure: process.env.NODE_ENV === 'production',  // HTTPS only in prod
      sameSite: 'strict',
      maxAge: 30 * 24 * 60 * 60 * 1000,  // 30 days in ms
    });

    // Send access token in response body (client stores in memory)
    res.json({
      accessToken,
      user: { id: user._id, email: user.email, role: user.role },
    });
  } catch (err) {
    res.status(500).json({ error: 'Login failed' });
  }
});
```

## 💻 Code Example — Advanced

```javascript
// advanced-jwt.js — Access + Refresh Token rotation + Blacklisting

const express = require('express');
const jwt = require('jsonwebtoken');
const redis = require('ioredis');  // for token blacklisting

const app = express();
const redisClient = new redis(process.env.REDIS_URL);

// ─── 1. AUTHENTICATION MIDDLEWARE ─────────────────────────────────────────────
const authenticate = async (req, res, next) => {
  const authHeader = req.headers.authorization;

  if (!authHeader?.startsWith('Bearer ')) {
    return res.status(401).json({ error: 'No token provided' });
  }

  const token = authHeader.split(' ')[1];

  // Check if token is blacklisted (revoked via logout)
  const isBlacklisted = await redisClient.get(`blacklist:${token}`);
  if (isBlacklisted) {
    return res.status(401).json({ error: 'Token has been revoked' });
  }

  const { valid, expired, payload, error } = verifyAccessToken(token);

  if (!valid) {
    if (expired) {
      return res.status(401).json({ error: 'Token expired', code: 'TOKEN_EXPIRED' });
    }
    return res.status(401).json({ error });
  }

  req.user = payload;
  req.token = token;  // store for potential blacklisting
  next();
};

// ─── 2. RBAC MIDDLEWARE (Role-Based Access Control) ───────────────────────────
const authorize = (...roles) => {
  return (req, res, next) => {
    if (!roles.includes(req.user.role)) {
      return res.status(403).json({
        error: `Access denied. Required roles: ${roles.join(', ')}`,
      });
    }
    next();
  };
};

// Usage:
app.get('/admin/users', authenticate, authorize('admin'), (req, res) => {
  res.json({ message: 'Admin only route' });
});
app.get('/dashboard', authenticate, authorize('admin', 'user'), (req, res) => {
  res.json({ message: 'User or admin' });
});

// ─── 3. REFRESH TOKEN ENDPOINT ────────────────────────────────────────────────
app.post('/auth/refresh', async (req, res) => {
  const refreshToken = req.cookies.refreshToken;  // from HttpOnly cookie

  if (!refreshToken) {
    return res.status(401).json({ error: 'No refresh token' });
  }

  try {
    // Verify refresh token
    const decoded = jwt.verify(refreshToken, JWT_REFRESH_SECRET);

    // Check if refresh token exists in DB (detect reuse)
    const user = await User.findOne({
      _id: decoded.userId,
      'refreshTokens.token': refreshToken,
    });

    if (!user) {
      // Token not in DB — possible token reuse attack!
      // Invalidate ALL refresh tokens for this user
      await User.findByIdAndUpdate(decoded.userId, { refreshTokens: [] });
      return res.status(401).json({ error: 'Invalid refresh token' });
    }

    // Rotate: delete old refresh token, create new one
    await User.findByIdAndUpdate(user._id, {
      $pull: { refreshTokens: { token: refreshToken } },  // remove old
    });

    const { accessToken, refreshToken: newRefreshToken } = generateTokens(user);

    // Store new refresh token
    await User.findByIdAndUpdate(user._id, {
      $push: { refreshTokens: { token: newRefreshToken, createdAt: new Date() } },
    });

    // Set new refresh token cookie
    res.cookie('refreshToken', newRefreshToken, {
      httpOnly: true,
      secure: process.env.NODE_ENV === 'production',
      sameSite: 'strict',
      maxAge: 30 * 24 * 60 * 60 * 1000,
    });

    res.json({ accessToken });
  } catch (err) {
    if (err.name === 'TokenExpiredError') {
      return res.status(401).json({ error: 'Refresh token expired, please login again' });
    }
    res.status(401).json({ error: 'Invalid refresh token' });
  }
});

// ─── 4. LOGOUT — blacklist access token + remove refresh token ───────────────
app.post('/auth/logout', authenticate, async (req, res) => {
  const { token, user } = req;

  // Blacklist access token in Redis until it expires naturally
  const decoded = jwt.decode(token);
  const ttl = decoded.exp - Math.floor(Date.now() / 1000);
  if (ttl > 0) {
    await redisClient.setex(`blacklist:${token}`, ttl, '1');
  }

  // Remove all refresh tokens (logout from all devices)
  await User.findByIdAndUpdate(user.userId, { refreshTokens: [] });

  res.clearCookie('refreshToken');
  res.json({ message: 'Logged out successfully' });
});
```

## 🟠 Express.js Integration

```javascript
// Complete auth flow with Express Router
const router = express.Router();

// Register
router.post('/register', async (req, res, next) => {
  try {
    const { email, password, name } = req.body;

    // Check if user exists
    const existing = await User.findOne({ email });
    if (existing) {
      return res.status(409).json({ error: 'Email already registered' });
    }

    // Hash password
    const passwordHash = await bcrypt.hash(password, 12);  // 12 rounds
    
    const user = await User.create({ email, passwordHash, name });
    const { accessToken, refreshToken } = generateTokens(user);

    res.cookie('refreshToken', refreshToken, { httpOnly: true, secure: true });
    res.status(201).json({ accessToken, user: { id: user._id, email } });
  } catch (err) {
    next(err);
  }
});

// Protected route example
router.get('/me', authenticate, async (req, res) => {
  // req.user is set by authenticate middleware
  const user = await User.findById(req.user.userId).select('-passwordHash -refreshTokens');
  res.json({ user });
});

// Change password (requires current password + valid JWT)
router.put('/change-password', authenticate, async (req, res, next) => {
  try {
    const { currentPassword, newPassword } = req.body;
    const user = await User.findById(req.user.userId);

    const valid = await bcrypt.compare(currentPassword, user.passwordHash);
    if (!valid) {
      return res.status(401).json({ error: 'Current password incorrect' });
    }

    user.passwordHash = await bcrypt.hash(newPassword, 12);
    user.refreshTokens = [];  // invalidate all sessions on password change
    await user.save();

    res.json({ message: 'Password changed. Please login again.' });
  } catch (err) {
    next(err);
  }
});

module.exports = router;
```

## ⚠️ Common Mistakes to Avoid

❌ **Mistake 1:** Storing JWT in localStorage
```javascript
// WRONG: localStorage is accessible by any JS (XSS attack target!)
localStorage.setItem('token', accessToken);

// CORRECT options:
// 1. Access token in memory (variable) — lost on page refresh, but safest from XSS
// 2. Refresh token in HttpOnly cookie (not accessible by JS)
// 3. Short-lived access token in memory + long-lived refresh in HttpOnly cookie
```

❌ **Mistake 2:** Never expiring tokens
```javascript
// WRONG: JWT that never expires
jwt.sign({ userId: '123' }, secret, { expiresIn: '100y' });  // effectively never
// If this token is stolen → attacker has access forever!

// CORRECT: Short access token + refresh token pattern
jwt.sign(payload, secret, { expiresIn: '15m' });  // access token
jwt.sign({ userId }, refreshSecret, { expiresIn: '30d' });  // refresh token
```

❌ **Mistake 3:** Putting sensitive data in payload
```javascript
// WRONG: Payload is just Base64 encoded — anyone can decode it!
jwt.sign({
  userId: '123',
  password: 'hashedpassword',  // ❌ never!
  creditCard: '4111111111111111',  // ❌ never!
  ssn: '123-45-6789',  // ❌ never!
}, secret);

// CORRECT: Only non-sensitive identification data
jwt.sign({
  userId: '123',
  email: 'user@example.com',
  role: 'user',
}, secret);
```

❌ **Mistake 4:** Using same secret for access + refresh tokens
```javascript
// WRONG: If secret leaks, both tokens are compromised
jwt.sign(payload, JWT_SECRET, { expiresIn: '15m' });
jwt.sign(payload, JWT_SECRET, { expiresIn: '30d' });  // same secret!

// CORRECT: Separate secrets
jwt.sign(payload, JWT_ACCESS_SECRET, { expiresIn: '15m' });
jwt.sign(payload, JWT_REFRESH_SECRET, { expiresIn: '30d' });
```

## 🧠 Tricky Interview Question

**Q: How do you invalidate/revoke a JWT before it expires?**

**Answer:** JWT is stateless — the server doesn't store it, so there's no "delete" mechanism. Options: (1) **Blacklist in Redis:** on logout, store the token in Redis with TTL = token's remaining expiry time. Auth middleware checks Redis before accepting any token. (2) **Refresh Token rotation:** keep refresh tokens in DB — on logout, delete from DB. Access tokens still valid until expiry, but can't be renewed. (3) **Short expiry:** 15-minute access tokens limit damage window — stolen token expires quickly. (4) **Version field:** store `tokenVersion` in user DB; include in JWT payload. On logout/compromise, increment DB version — old tokens with wrong version are rejected. Trade-off: all require at least one DB/Redis lookup, sacrificing full statelessness.

## ⚫ Interview Questions + Answers

**Q1: What are the 3 parts of a JWT and what does each contain?**
A1: **Header**: algorithm used (HS256, RS256) and token type ("JWT") — Base64URL encoded. **Payload**: claims — standard (`iat` issued-at, `exp` expiry, `sub` subject, `iss` issuer, `aud` audience) and custom (`userId`, `email`, `role`) — Base64URL encoded, NOT encrypted. **Signature**: HMAC(header + "." + payload, secret) for HS256, or RSA(header + "." + payload, private_key) for RS256. Signature ensures payload wasn't tampered with; if modified, signature won't match.

**Q2: What is the difference between HS256 and RS256?**
A2: **HS256 (HMAC-SHA256)**: symmetric — same secret key used to sign and verify. Simple, fast. Problem: every service that needs to verify tokens must have the secret — if any service is compromised, the secret leaks. **RS256 (RSA-SHA256)**: asymmetric — private key signs (only auth service has it), public key verifies (all services can have it). Services can verify JWTs without having signing capability. Better for microservices. Use HS256 for simple single-server apps; RS256 for microservices or when tokens are verified by third parties.

**Q3: What is the Access Token + Refresh Token pattern?**
A3: **Access Token**: short-lived (15 min), stored in memory, sent in every API request (`Authorization: Bearer <token>`). **Refresh Token**: long-lived (30 days), stored in HttpOnly cookie (can't be accessed by JS), used ONLY to get new access tokens. Flow: login → get both tokens → access token for requests → when access token expires (15 min) → use refresh token to silently get new access token → user never notices. Advantage: if access token is stolen, it expires in 15 min. Refresh token in HttpOnly cookie protects against XSS.

**Q4: Why should you never store JWT in localStorage?**
A4: localStorage is accessible by any JavaScript on the page. If your app has an XSS (Cross-Site Scripting) vulnerability — even in a third-party library — the attacker's script can read `localStorage.getItem('token')` and steal the token. Better options: (1) Access token in JavaScript memory (variable) — gone on page refresh but safest from XSS. (2) HttpOnly cookie — JavaScript cannot read it at all; immune to XSS token theft (though vulnerable to CSRF if not using `SameSite: Strict`).

**Q5: What happens when a JWT secret leaks in production?**
A5: Attacker can forge ANY JWT — create tokens with `role: 'admin'`, any `userId`, never-expiring tokens. Immediate actions: (1) Rotate the secret — invalidates ALL existing tokens (all users logged out). (2) Force all users to re-login. (3) Audit logs for suspicious activity during the window. Prevention: store secrets in environment variables (never in code), use secrets management (AWS Secrets Manager, HashiCorp Vault), rotate secrets regularly, use RS256 (private key only on auth server, harder to steal than HS256 shared secret).
