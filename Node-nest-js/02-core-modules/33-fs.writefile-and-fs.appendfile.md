# 33. fs.writeFile + fs.appendFile
# हिंदी में: fs.writeFile + fs.appendFile — Files में लिखना

---

## 🔵 Simple Definition (English)
`fs.writeFile()` creates a new file or **completely overwrites** an existing one with new content. `fs.appendFile()` **adds content to the end** of a file without touching what's already there, creating the file if it doesn't exist yet.

## 🔵 सरल परिभाषा (Hindi)
`fs.writeFile()` नई file बनाता है या existing file को नए content से **पूरी तरह overwrite** करता है। `fs.appendFile()` file के end में content **add** करता है बिना जो already है उसे छुए, अगर file exist नहीं करती तो बना देता है।

---

## 🔴 Problem it Solves
Applications need two fundamentally different write patterns: (1) saving a complete, final version of data (e.g., a generated report, a user's profile JSON, a config snapshot) where the old content is irrelevant and should be replaced entirely, and (2) accumulating an ongoing record over time (e.g., log files, audit trails, event histories) where EVERY previous entry must be preserved and new entries just add on. Using the wrong one causes real bugs — overwriting a log file destroys history; appending to what should be a fresh file leaves stale duplicate data.

## 🔴 यह क्यों बना? (Hindi)
Applications को दो fundamentally अलग write patterns चाहिए: (1) data का complete, final version save करना (जैसे generated report, user का profile JSON, config snapshot) जहाँ पुराना content irrelevant है और पूरी तरह replace होना चाहिए, और (2) समय के साथ ongoing record जमा करना (जैसे log files, audit trails, event histories) जहाँ हर पुरानी entry preserve होनी चाहिए और नई entries बस add होती रहें। गलत वाला use करने से real bugs होते हैं — log file overwrite करने से history destroy हो जाती है; fresh file होनी चाहिए उसमें append करने से stale duplicate data रह जाता है।

---

## 🟢 How it Works — Step by Step

Step 1 → `fs.writeFile(path, data, callback)` or `await fs.promises.writeFile(path, data)` opens the file in **truncate mode** — if content already exists, it's wiped BEFORE the new data is written. If the file doesn't exist, it's created.
Step 2 → `fs.appendFile(path, data, callback)` or `await fs.promises.appendFile(path, data)` opens the file in **append mode** — the write cursor starts at the END of existing content, new data is added after it. If the file doesn't exist, it's created (starting empty).
Step 3 → Both accept an `encoding` option (default `'utf8'` for strings) or can write raw `Buffer`/binary data directly.
Step 4 → Both support a `flag` option for finer control: `'w'` (write/truncate, default for writeFile), `'a'` (append, default for appendFile), `'wx'`/`'ax'` (fail if file already exists — useful to prevent accidental overwrites).
Step 5 → `writeFile` is NOT safe for concurrent partial writes — if the process crashes mid-write, the file can be left truncated/corrupted. For critical atomic writes, write to a temp file then `fs.rename()` it into place (rename is atomic on most filesystems).
Step 6 → Repeated `appendFile` calls in a tight loop are inefficient (each call opens/writes/closes the file descriptor); for high-frequency logging, use a persistent `fs.createWriteStream(path, { flags: 'a' })` kept open across many writes instead.

## 🟢 कैसे काम करता है? (Hindi)
Step 1 → `fs.writeFile(path, data, callback)` या `await fs.promises.writeFile(path, data)` file को **truncate mode** में खोलता है — अगर content already है तो नया data लिखने से PEHLE wipe हो जाता है। File न हो तो बन जाती है।
Step 2 → `fs.appendFile(path, data, callback)` या `await fs.promises.appendFile(path, data)` file को **append mode** में खोलता है — write cursor existing content के END पर शुरू होता है, नया data उसके बाद add होता है। File न हो तो बन जाती है (खाली शुरू होकर)।
Step 3 → दोनों `encoding` option accept करते हैं (default `'utf8'` strings के लिए) या directly raw `Buffer`/binary data लिख सकते हैं।
Step 4 → दोनों finer control के लिए `flag` option support करते हैं: `'w'` (write/truncate, writeFile का default), `'a'` (append, appendFile का default), `'wx'`/`'ax'` (file already exist हो तो fail — accidental overwrite रोकने के लिए useful)।
Step 5 → `writeFile` concurrent partial writes के लिए safe नहीं है — process बीच में crash हो तो file truncated/corrupted रह सकती है। Critical atomic writes के लिए, temp file में लिखो फिर `fs.rename()` करो (rename अधिकतर filesystems पर atomic है)।
Step 6 → Tight loop में repeated `appendFile` calls inefficient हैं (हर call file descriptor open/write/close करती है); high-frequency logging के लिए, बहुत सारी writes के लिए खुला रहने वाला `fs.createWriteStream(path, { flags: 'a' })` use करो।

## 🟡 Real World Example
**Amazon's order-processing audit system:** Every state change on an order (`placed` → `confirmed` → `shipped` → `delivered`) is appended as a new line to `orders-audit.log` via `fs.appendFile()` — NEVER overwritten, forming a permanent, chronological record for compliance and dispute resolution. Meanwhile, the daily "current inventory snapshot" report is regenerated and saved fresh each night using `fs.writeFile()`, completely replacing yesterday's snapshot since only the LATEST inventory state matters for that specific file.

## 🟡 Real Example Hindi mein
**Amazon का order-processing audit system:** Order पर हर state change (`placed` → `confirmed` → `shipped` → `delivered`) `fs.appendFile()` से `orders-audit.log` में नई line की तरह add होता है — कभी overwrite नहीं होता, compliance और dispute resolution के लिए permanent, chronological record बनाता है। वहीं daily "current inventory snapshot" report हर रात fresh regenerate और `fs.writeFile()` से save होती है, कल का snapshot पूरी तरह replace करती है क्योंकि उस specific file के लिए केवल LATEST inventory state matter करता है।

## 💻 Code Example — Basic

```javascript
// writeAppendBasics.js
const fs = require('fs/promises');

async function main() {
  // writeFile — creates OR completely overwrites the file
  await fs.writeFile('./report.txt', 'Report generated at ' + new Date().toISOString() + '\n');
  console.log('report.txt written (fresh content)');

  // Calling writeFile AGAIN replaces everything — old content is GONE
  await fs.writeFile('./report.txt', 'New report content\n');
  const afterOverwrite = await fs.readFile('./report.txt', 'utf8');
  console.log('After overwrite:', afterOverwrite); // only "New report content" — old line is gone

  // appendFile — adds to the end, preserving what's there
  await fs.appendFile('./log.txt', `[${new Date().toISOString()}] Event 1\n`);
  await fs.appendFile('./log.txt', `[${new Date().toISOString()}] Event 2\n`);
  const logContent = await fs.readFile('./log.txt', 'utf8');
  console.log('Log content:', logContent); // BOTH lines present, in order
}

main().catch(console.error);
```

## 💻 Code Example — Advanced

```javascript
// safeWritePatterns.js — production-safe write patterns
const fs = require('fs/promises');
const path = require('path');
const { createWriteStream } = require('fs');

// ─── 1. ATOMIC WRITE via temp file + rename ─────────────────────────────────
// Prevents a crash mid-write from leaving a corrupted/truncated file
async function atomicWriteFile(filePath, data) {
  const tempPath = `${filePath}.tmp-${Date.now()}`; // unique temp filename
  await fs.writeFile(tempPath, data); // write fully to the temp location first
  await fs.rename(tempPath, filePath); // rename is ATOMIC on most filesystems — instant swap
}

// ─── 2. EXCLUSIVE WRITE — fail instead of silently overwriting ─────────────
async function writeIfNotExists(filePath, data) {
  try {
    await fs.writeFile(filePath, data, { flag: 'wx' }); // 'wx' = write, fail if exists
    return true;
  } catch (err) {
    if (err.code === 'EEXIST') {
      console.warn(`File already exists, refusing to overwrite: ${filePath}`);
      return false;
    }
    throw err;
  }
}

// ─── 3. HIGH-FREQUENCY LOGGING — persistent write stream instead of repeated appendFile ──
// appendFile() opens+writes+closes the fd EVERY call — expensive at high volume.
// A write stream keeps the fd open, batching writes efficiently.
class Logger {
  constructor(logPath) {
    // flags: 'a' = append mode, keeps adding without truncating
    this.stream = createWriteStream(logPath, { flags: 'a' });
  }
  log(message) {
    const line = `[${new Date().toISOString()}] ${message}\n`;
    this.stream.write(line); // much cheaper than appendFile() per call at high frequency
  }
  close() {
    this.stream.end(); // always close streams when done to flush buffered data
  }
}

(async () => {
  await atomicWriteFile('./config-snapshot.json', JSON.stringify({ version: 2 }, null, 2));
  console.log('Atomic write complete');

  const created = await writeIfNotExists('./important.lock', 'locked');
  console.log('Lock file created:', created);

  const logger = new Logger('./app.log');
  for (let i = 0; i < 1000; i++) {
    logger.log(`Processing item ${i}`); // efficient repeated writes via open stream
  }
  logger.close();
})();
```

## 🟠 Express.js Integration

```javascript
// server.js — writeFile for "save/replace" endpoints, appendFile for audit logging
const express = require('express');
const fs = require('fs/promises');
const path = require('path');

const app = express();
app.use(express.json());

// SAVE/REPLACE pattern: user's full profile document, overwritten on every update
app.put('/profile/:userId', async (req, res) => {
  const filePath = path.join(__dirname, 'profiles', `${req.params.userId}.json`);
  try {
    await fs.writeFile(filePath, JSON.stringify(req.body, null, 2)); // full overwrite
    res.json({ message: 'Profile saved' });
  } catch (err) {
    res.status(500).json({ error: 'Failed to save profile' });
  }
});

// AUDIT LOG pattern: append every action, never overwrite history
app.post('/orders/:orderId/status', async (req, res) => {
  const { status } = req.body;
  const logLine = `[${new Date().toISOString()}] Order ${req.params.orderId} → ${status}\n`;

  try {
    await fs.appendFile(path.join(__dirname, 'logs', 'order-audit.log'), logLine);
    res.json({ message: 'Status logged' });
  } catch (err) {
    res.status(500).json({ error: 'Failed to log status change' });
  }
});

app.listen(3000, () => console.log('Server running on port 3000'));
```

## ⚠️ Common Mistakes to Avoid

❌ Mistake 1: Using `writeFile` when you meant to accumulate log entries
```javascript
// Wrong — every call WIPES the previous log entries, only the last one survives!
fs.writeFile('./events.log', `Event: ${eventName}\n`, (err) => {});
// After 10 calls, events.log contains only the 10th event — 9 are lost

// Right — use appendFile to preserve history
fs.appendFile('./events.log', `Event: ${eventName}\n`, (err) => {});
// After 10 calls, all 10 events are present, in order
```

❌ Mistake 2: Calling `appendFile` in a tight loop without realizing the performance cost
```javascript
// Wrong — thousands of separate open/write/close cycles, very slow at scale
for (let i = 0; i < 100000; i++) {
  fs.appendFileSync('./bulk.log', `Line ${i}\n`); // 100,000 separate fd open/close ops
}

// Right — use a single open write stream for many sequential writes
const stream = fs.createWriteStream('./bulk.log', { flags: 'a' });
for (let i = 0; i < 100000; i++) {
  stream.write(`Line ${i}\n`); // fd stays open, much faster
}
stream.end();
```

## 🧠 Tricky Interview Question

```javascript
const fs = require('fs');

fs.writeFileSync('./data.txt', 'A');
fs.writeFileSync('./data.txt', 'B', { flag: 'a' });
console.log(fs.readFileSync('./data.txt', 'utf8')); // ?
```
Answer: Prints **`"AB"`**. Even though we're calling `writeFileSync` (not `appendFile`) the SECOND time, the explicit `{ flag: 'a' }` option OVERRIDES the function's default behavior and forces append mode instead of truncate mode. This shows that `writeFile`/`writeFileSync` and `appendFile`/`appendFileSync` are actually the SAME underlying operation with just different DEFAULT flags (`'w'` vs `'a'`) — you can make `writeFile` behave like append (or vice versa, making `appendFile` truncate with `{ flag: 'w' }`) by explicitly overriding the `flag` option. Many engineers assume these are fundamentally different APIs when they're really just different default configurations of the same syscall-level operation.

## ⚫ Interview Questions + Answers

Q1: What's the actual difference at the OS/syscall level between `writeFile` and `appendFile`?
A1: Both ultimately call the same underlying file-open syscall but with different default `flag` values. `writeFile` defaults to `'w'` (open for writing, truncate existing content to zero length first). `appendFile` defaults to `'a'` (open for writing, position the cursor at the END of existing content, never truncate). Both create the file if it doesn't already exist. You can override either's default flag explicitly to get the other's behavior, proving they're variations of the same core operation.

Q2: Is `fs.writeFile` atomic — i.e., if the process crashes mid-write, is the file guaranteed to be either fully old or fully new content?
A2: No — `writeFile` is NOT atomic by itself. If the process crashes partway through writing, the file can be left in a TRUNCATED, PARTIALLY-WRITTEN state (old content wiped, new content incomplete). For true atomicity, write to a temporary file first, then use `fs.rename()` to move it into the final location — rename operations are atomic on virtually all filesystems (the OS swaps the file reference instantly, no partial-state window).

Q3: Why is calling `fs.appendFileSync` repeatedly in a loop considered bad practice for high-volume logging?
A3: Each call to `appendFileSync`/`appendFile` independently opens a file descriptor, performs the write, and closes the descriptor — this open/close overhead is cheap for occasional calls but adds up significantly under high-frequency logging (thousands of log lines per second). A persistent `fs.createWriteStream(path, { flags: 'a' })`, opened ONCE and reused across many `.write()` calls, avoids this repeated overhead and also internally batches/buffers writes more efficiently.

Q4: What does the `'wx'` flag do, and when would you use it?
A4: `'wx'` means "write, but FAIL if the file already exists" (as opposed to plain `'w'` which silently truncates/overwrites). It's useful for preventing accidental double-writes or race conditions — e.g., creating a lock file, or ensuring you don't silently clobber an existing user-uploaded file with the same name. The write throws an `EEXIST` error instead of proceeding, forcing the calling code to explicitly handle the "already exists" case.

Q5: How would you safely write JSON data to a file, ensuring valid JSON even if the write is interrupted?
A5: Serialize the FULL object to a string first (`JSON.stringify(data, null, 2)`), write it entirely to a TEMPORARY file path, then atomically `fs.rename()` the temp file to the final target path. This guarantees that the final file either contains the complete, valid old JSON or the complete, valid new JSON — never a half-written, syntactically broken JSON file, which could happen if you wrote directly to the target path and the process crashed mid-write.

## 🔷 When to Use + When Not to Use
✅ Use `writeFile` when:
- Saving a complete, replaceable snapshot of data (config, generated report, user profile JSON).
- You want the file to contain ONLY the latest content, discarding anything old.

✅ Use `appendFile` when:
- Building logs, audit trails, or any chronological record where history must be preserved.
- Adding entries incrementally over time without rewriting the whole file each time.

❌ Avoid:
- `appendFile` in a tight high-frequency loop — use a persistent write stream instead.
- Plain `writeFile` for critical data without atomic temp-file+rename when crash-safety matters.
