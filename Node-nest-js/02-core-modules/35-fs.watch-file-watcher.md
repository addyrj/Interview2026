# 35. fs.watch — File Watcher
# हिंदी में: fs.watch — Files को Real-Time Monitor करना

---

## 🔵 Simple Definition (English)
`fs.watch()` lets you monitor a file or directory for changes (modifications, renames, deletions) and react to them in real time via an event-based callback — instead of repeatedly checking ("polling") the file yourself.

## 🔵 सरल परिभाषा (Hindi)
`fs.watch()` किसी file या directory को changes (modifications, renames, deletions) के लिए monitor करने देता है और event-based callback से real time में react करता है — बार-बार खुद check ("polling") करने की जगह।

---

## 🔴 Problem it Solves
Many tools need to react when files change: dev servers that auto-reload when source code changes (nodemon, webpack dev server), config systems that hot-reload settings without restarting, log-tailing tools, sync utilities. Checking "has this file changed?" manually in a loop (polling with `setInterval` + `fs.stat`) wastes CPU and introduces latency. `fs.watch()` uses the OS's native filesystem notification APIs (inotify on Linux, FSEvents on macOS, ReadDirectoryChangesW on Windows) to get INSTANT notification the moment something changes, with near-zero overhead while idle.

## 🔴 यह क्यों बना? (Hindi)
बहुत सारे tools को files बदलने पर react करना होता है: source code बदलने पर auto-reload करने वाले dev servers (nodemon, webpack dev server), restart किए बिना settings hot-reload करने वाले config systems, log-tailing tools, sync utilities। "क्या यह file बदली?" manually loop में check करना (polling with `setInterval` + `fs.stat`) CPU waste करता है और latency लाता है। `fs.watch()` OS की native filesystem notification APIs use करता है (Linux पर inotify, macOS पर FSEvents, Windows पर ReadDirectoryChangesW) कुछ भी बदलने पर INSTANT notification पाने के लिए, idle रहते near-zero overhead के साथ।

---

## 🟢 How it Works — Step by Step

Step 1 → `fs.watch(path, options, listener)` registers a watcher on `path` (file or directory). Returns an `FSWatcher` instance (an EventEmitter).
Step 2 → The listener fires with `(eventType, filename)` — `eventType` is `'change'` (content modified) or `'rename'` (file created, deleted, OR actually renamed — Node lumps these together confusingly).
Step 3 → Pass `{ recursive: true }` (supported on macOS and Windows, NOT reliably on Linux) to watch an entire directory tree, not just the top-level folder.
Step 4 → `fs.watch` behavior is notoriously PLATFORM-INCONSISTENT — event firing frequency, whether `filename` is provided, and recursive support all vary across OSes. This is its biggest practical limitation.
Step 5 → Because of this inconsistency, production tools (nodemon, webpack, chokidar) typically use the `chokidar` npm package instead, which wraps `fs.watch`/polling fallbacks into a consistent, reliable cross-platform API.
Step 6 → Always call `watcher.close()` when done watching to release the underlying OS resource — an unclosed watcher keeps the process alive and leaks resources.

## 🟢 कैसे काम करता है? (Hindi)
Step 1 → `fs.watch(path, options, listener)` `path` (file या directory) पर एक watcher register करता है। `FSWatcher` instance return करता है (एक EventEmitter)।
Step 2 → Listener `(eventType, filename)` के साथ fire होता है — `eventType` `'change'` (content modified) या `'rename'` (file बनी, delete हुई, या actually rename हुई — Node इन्हें confusingly एक साथ रखता है)।

Step 6 → Watching खत्म होने पर हमेशा `watcher.close()` call करो underlying OS resource release करने के लिए — unclosed watcher process को alive रखता है और resources leak करता है।

## 💻 Code Example — Basic

```javascript
// watchBasics.js — watching a single file for changes
const fs = require('fs');

console.log('Watching config.json for changes...');

const watcher = fs.watch('./config.json', (eventType, filename) => {
  console.log(`Event: ${eventType}, File: ${filename}`);
  // eventType is typically 'change' when content is modified
  // filename may be null on some platforms/edge cases — don't rely on it alone
});

// Simulate a change after 2 seconds (in real use, this would be an external edit)
setTimeout(() => {
  fs.writeFileSync('./config.json', JSON.stringify({ updated: true }));
}, 2000);

// Always close the watcher when you're done, to release the OS resource
setTimeout(() => {
  watcher.close();
  console.log('Stopped watching.');
}, 5000);
```

## 💻 Code Example — Advanced

```javascript
// configHotReload.js — production pattern: debounced reload + graceful error handling
const fs = require('fs');
const path = require('path');

class ConfigWatcher {
  constructor(configPath) {
    this.configPath = configPath;
    this.config = {};
    this.debounceTimer = null;
    this.loadConfig(); // initial load before watching starts
    this.startWatching();
  }

  loadConfig() {
    try {
      const raw = fs.readFileSync(this.configPath, 'utf8');
      this.config = JSON.parse(raw);
      console.log('Config reloaded:', this.config);
    } catch (err) {
      // Don't crash on a transient read error (e.g., file mid-write) — keep old config
      console.error('Failed to reload config, keeping previous version:', err.message);
    }
  }

  startWatching() {
    this.watcher = fs.watch(this.configPath, (eventType) => {
      if (eventType !== 'change') return; // ignore rename-type events here

      // DEBOUNCE: many editors trigger multiple 'change' events for ONE save
      // (e.g., write + metadata update) — wait briefly to avoid redundant reloads
      clearTimeout(this.debounceTimer);
      this.debounceTimer = setTimeout(() => this.loadConfig(), 100);
    });

    this.watcher.on('error', (err) => {
      // fs.watch can emit errors (e.g., file deleted while watching) — handle, don't crash
      console.error('Watcher error:', err.message);
    });
  }

  get(key) {
    return this.config[key];
  }

  stop() {
    this.watcher.close(); // release the OS-level watch handle
  }
}

const configWatcher = new ConfigWatcher('./app-config.json');

// Elsewhere in the app, always read the LATEST value via the watcher instance:
setInterval(() => {
  console.log('Current feature flag:', configWatcher.get('featureFlagX'));
}, 3000);

// On graceful shutdown:
process.on('SIGTERM', () => {
  configWatcher.stop();
  process.exit(0);
});
```

## 🟠 Express.js Integration

```javascript
// server.js — Express app with live-reloading feature flags via fs.watch
const express = require('express');
const fs = require('fs');
const path = require('path');

const app = express();
const flagsPath = path.join(__dirname, 'feature-flags.json');

let featureFlags = JSON.parse(fs.readFileSync(flagsPath, 'utf8')); // initial load

// Watch for changes (e.g., an ops engineer edits the flags file, or a sidecar
// container writes new flags pulled from a remote config service)
fs.watch(flagsPath, (eventType) => {
  if (eventType === 'change') {
    try {
      featureFlags = JSON.parse(fs.readFileSync(flagsPath, 'utf8'));
      console.log('Feature flags reloaded:', featureFlags);
    } catch (err) {
      console.error('Invalid feature-flags.json, keeping old flags:', err.message);
    }
  }
});

app.get('/checkout', (req, res) => {
  // Reads the LATEST in-memory flags — no restart needed when flags.json changes
  if (featureFlags.newCheckoutFlow) {
    return res.json({ flow: 'new', version: 2 });
  }
  res.json({ flow: 'legacy', version: 1 });
});

app.listen(3000, () => console.log('Server running on port 3000'));
```

## ⚠️ Common Mistakes to Avoid

❌ Mistake 1: Not handling the "double-fire" behavior of `fs.watch`
```javascript
// Wrong — assumes ONE save triggers exactly ONE 'change' event
fs.watch('./config.json', () => {
  reloadConfigExpensively(); // may run 2-3 times for a SINGLE file save, wasting work
});

// Right — debounce rapid-fire events into one actual reload
let timer;
fs.watch('./config.json', () => {
  clearTimeout(timer);
  timer = setTimeout(reloadConfigExpensively, 100); // collapse bursts into one call
});
```

❌ Mistake 2: Forgetting to close the watcher, leaking resources / keeping the process alive
```javascript
// Wrong — watcher never closed, process never exits cleanly, OS handle leaks
function startTempWatch() {
  fs.watch('./temp.txt', () => console.log('changed'));
} // no reference kept, no way to close it later

// Right — keep a reference and close it when done
function startTempWatch() {
  const watcher = fs.watch('./temp.txt', () => console.log('changed'));
  return watcher; // caller can call watcher.close() later
}
const w = startTempWatch();
// ... later ...
w.close();
```

## 🧠 Tricky Interview Question

```javascript
const fs = require('fs');
fs.writeFileSync('./watched.txt', 'initial');

const watcher = fs.watch('./watched.txt', (eventType, filename) => {
  console.log(eventType, filename);
});

fs.writeFileSync('./watched.txt', 'updated'); // one logical "save"
// How many times might the callback fire, and why?
```
Answer: It can fire **more than once** (commonly twice) for what looks like a single logical write. This is because many editors/OS filesystem layers perform a write as multiple discrete operations under the hood (e.g., truncate + write content, or write to a temp file + rename), and each discrete operation can independently trigger a filesystem-level notification. `fs.watch`'s event granularity is tied to low-level OS events, not to the application-level concept of "one save" — which is exactly why production code DEBOUNCES the callback (waits a short delay, collapsing bursts of events into a single reaction) rather than reacting to every raw fire immediately.

## ⚫ Interview Questions + Answers

Q1: Why is `fs.watch` considered unreliable across different operating systems?
A1: `fs.watch` is a thin wrapper around EACH OS's native file-notification mechanism — inotify (Linux), FSEvents (macOS), ReadDirectoryChangesW (Windows) — and these systems have different capabilities and quirks. For example, recursive directory watching (`{ recursive: true }`) works on macOS and Windows but is NOT reliably supported on Linux. Event firing frequency and whether the `filename` argument is populated also vary by platform. This inconsistency is why most production tooling uses the `chokidar` package, which normalizes these differences into one predictable API.

Q2: What's the difference between `fs.watch` and `fs.watchFile`?
A2: `fs.watch` uses OS-native file-system events (fast, low overhead, but platform-inconsistent). `fs.watchFile` uses POLLING — it periodically checks the file's stats (`stat`) at a configurable interval and compares timestamps to detect changes. Polling is slower to detect changes and uses more CPU over time, but is more PREDICTABLE and consistent across platforms/network filesystems (NFS) where native OS events sometimes don't fire reliably. Choose `watchFile` when consistency matters more than speed, or on network drives where `fs.watch` may silently fail to detect changes.

Q3: Why should you always debounce `fs.watch` callbacks in production code?
A3: A single logical file save can trigger MULTIPLE raw filesystem events (truncate+write, metadata update, or editor-specific save-via-temp-file-then-rename patterns), causing the callback to fire 2-3+ times for what the user considers "one save." Debouncing (delaying the actual reaction by a short window and collapsing repeated triggers within that window into one execution) avoids redundant, expensive work like re-parsing a config file or restarting a process multiple times unnecessarily.

Q4: How do you properly clean up an `fs.watch` watcher?
A4: Keep a reference to the `FSWatcher` instance returned by `fs.watch()`, and call `.close()` on it once you no longer need to watch (e.g., in a shutdown handler, or when a temporary watch's purpose is fulfilled). An unclosed watcher holds an open OS-level file handle/descriptor and can prevent the Node process from exiting naturally, since active watchers count as "pending work" keeping the event loop alive.

Q5: When would you prefer the `chokidar` npm package over raw `fs.watch`?
A5: Whenever you need: reliable recursive directory watching across ALL platforms (not just macOS/Windows), built-in debouncing/stability thresholds (waiting for a file to "settle" before firing, useful for large file writes), ignoring patterns (e.g., skip `node_modules`, `.git`), and consistent behavior regardless of the underlying OS's native quirks. Essentially any production-grade file-watching feature (dev server hot-reload, build tools, sync utilities) should use `chokidar` rather than relying on `fs.watch` directly.

## 🔷 When to Use + When Not to Use
✅ Use when:
- Building dev-server hot-reload or build-watch tooling (though prefer `chokidar` for robustness).
- Reloading config/feature-flag files live without restarting the process.
- Simple, single-file watch needs in internal tools where platform inconsistency is acceptable.

❌ Avoid when:
- You need guaranteed, consistent cross-platform recursive directory watching — use `chokidar` instead.
- Watching files on network filesystems (NFS, some cloud-mounted volumes) where native OS events may not propagate — use `fs.watchFile` (polling) instead.
- You haven't implemented debouncing — raw unthrottled reactions to every fired event waste resources and can cause race conditions.
