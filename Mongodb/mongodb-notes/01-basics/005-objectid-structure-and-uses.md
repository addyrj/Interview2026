# 5. ObjectId — structure and uses
# हिंदी में: ObjectId — संरचना और उपयोग

---

## 🔵 Simple Definition (English)
An **ObjectId** is MongoDB's default 12-byte identifier for the `_id` field. It is shown as a 24-character hexadecimal string such as `507f1f77bcf86cd799439011`. Its 12 bytes are: **4 bytes timestamp** (seconds since the Unix epoch) + **5 bytes random value** (unique per process/machine) + **3 bytes incrementing counter**. It is generated by the **driver (client side)**, is roughly time-ordered, and is globally unique without any central coordinator.

## 🔵 सरल परिभाषा (Hindi)
**ObjectId** `_id` field के लिए MongoDB का default 12-byte identifier है। यह 24 अक्षरों की hexadecimal string की तरह दिखता है, जैसे `507f1f77bcf86cd799439011`। इसके 12 bytes हैं: **4 bytes timestamp** (Unix epoch से seconds) + **5 bytes random value** (process/machine के हिसाब से unique) + **3 bytes बढ़ता counter**। इसे **driver (client side)** बनाता है, यह लगभग समय-क्रम में होता है, और बिना किसी central coordinator के globally unique रहता है।

---

## 🔴 Problem it Solves
SQL's auto-increment id needs a central counter: in a distributed or sharded system, every insert would have to ask one node for the next number (bottleneck), and ids are guessable (`/user/101`). A UUID is unique but 16 bytes, random (poor index locality) and carries no time. ObjectId lets **any app server generate ids offline**, with practically zero collision chance, small size (12 bytes), embedded creation time (no separate `createdAt` needed for rough ordering), and good B-tree insert locality because new ids are almost always larger than old ones.

## 🔴 यह क्यों बना? (Hindi)
SQL के auto-increment id को central counter चाहिए: distributed या sharded system में हर insert को अगला number किसी एक node से पूछना पड़ता (bottleneck), और ids guess हो जाते हैं (`/user/101`)। UUID unique है पर 16 bytes, random (index locality खराब) और समय-रहित है। ObjectId से **कोई भी app server offline id बना सकता है**, collision की संभावना लगभग शून्य, छोटा size (12 bytes), embedded creation time (मोटे क्रम के लिए अलग `createdAt` नहीं चाहिए), और अच्छी B-tree insert locality क्योंकि नए ids लगभग हमेशा पुराने से बड़े होते हैं।

---

## 🟢 How it Works — Step by Step

Step 1 → You call `insertOne({ ... })` without an `_id`. The **driver** creates `new ObjectId()` before sending the document.
Step 2 → Bytes 0-3: current Unix time in seconds (big-endian). Example `507f1f77` = 1350508407 = 17 Oct 2012 21:13:27 UTC.
Step 3 → Bytes 4-8: a random 5-byte value generated once per process (older docs call it machine id + pid).
Step 4 → Bytes 9-11: a 3-byte counter, started at a random number and incremented per id (so 16.7 million ids per second per process before wrap).
Step 5 → The 12 bytes are hex-encoded into 24 characters when shown, but stored as **12 raw bytes** (BSON type ObjectId), not as a string.
Step 6 → Because the timestamp leads, sorting by `_id` approximates sorting by creation time, and `getTimestamp()` extracts the time.

## 🟢 कैसे काम करता है? (Hindi)
Step 1 → आप बिना `_id` के `insertOne({ ... })` करते हो। **Driver** document भेजने से पहले `new ObjectId()` बना देता है।
Step 2 → Bytes 0-3: मौजूदा Unix time seconds में (big-endian)। उदाहरण `507f1f77` = 1350508407 = 17 Oct 2012 21:13:27 UTC।
Step 3 → Bytes 4-8: 5-byte random value जो हर process के लिए एक बार बनती है (पुराने docs इसे machine id + pid कहते हैं)।
Step 4 → Bytes 9-11: 3-byte counter, random संख्या से शुरू होकर हर id पर +1 (wrap होने से पहले प्रति process प्रति second 1.67 करोड़ ids)।
Step 5 → दिखाते समय 12 bytes 24 अक्षरों की hex में बदलते हैं, पर store **12 raw bytes** (BSON type ObjectId) के रूप में होते हैं, string नहीं।
Step 6 → Timestamp सबसे आगे होने से `_id` से sort करना लगभग creation-time से sort करने जैसा है, और `getTimestamp()` से समय निकलता है।

## 🟡 Real World Example
**Swiggy order ids** inside a MongoDB-backed tracking service: every order-tracking event gets an ObjectId generated by the Node.js server handling the request - no round trip to the database for an id, and thousands of servers can do it simultaneously. To find "events created in the last hour" without a `createdAt` index, the team queries `_id` greater than `ObjectId.createFromTime(now - 3600)`, which uses the default `_id` index. Caution: they never expose raw ObjectIds as secrets, because the timestamp and structure leak information.

## 🟡 Real Example Hindi mein
**Swiggy के order ids**, MongoDB-backed tracking service में: हर order-tracking event का ObjectId उस request को संभालने वाला Node.js server बनाता है - id के लिए database तक round trip नहीं, और हज़ारों servers एक साथ बना सकते हैं। "पिछले एक घंटे के events" बिना `createdAt` index के निकालने के लिए team `_id` को `ObjectId.createFromTime(now - 3600)` से बड़ा query करती है, जो default `_id` index इस्तेमाल करती है। सावधानी: raw ObjectId को secret की तरह expose नहीं करते, क्योंकि timestamp और structure जानकारी leak करते हैं।

## 💻 Code Example — Basic

Verified on mongod 8.0.4 / mongosh (new ids vary on every run; the fixed id below is deterministic).

```javascript
// Create a fresh id (value differs every run)
const id = new ObjectId()
id.toString().length          // Output: 24   (hex characters)
typeof id.toString()          // Output: 'string'

// Decode a known id
const o = ObjectId('507f1f77bcf86cd799439011')
o.getTimestamp().toISOString()   // Output: '2012-10-17T21:13:27.000Z'  (first 4 bytes)
o.toString().slice(0, 8)         // '507f1f77'  = timestamp part
o.toString().slice(8, 18)        // 'bcf86cd799' = 5 random bytes
o.toString().slice(18)           // '439011'     = 3-byte counter
parseInt('507f1f77', 16)         // Output: 1350508407 (seconds since epoch)

// Two ids from the same process share the middle part; the counter increments by 1
const a = ObjectId(), b = ObjectId()
a.toString().slice(8, 18) === b.toString().slice(8, 18)                        // Output: true
parseInt(b.toString().slice(18), 16) - parseInt(a.toString().slice(18), 16)    // Output: 1

// Equality and validity
ObjectId('507f1f77bcf86cd799439011').equals(o)   // Output: true
ObjectId.isValid('abc')                           // Output: false
ObjectId.isValid('507f1f77bcf86cd799439011')      // Output: true
```

## 💻 Code Example — Advanced

```javascript
// Time-range query using only the _id index (no createdAt field required)
// createFromTime(seconds) builds an ObjectId whose timestamp part is that time and the rest zeros
ObjectId.createFromTime(0).toString()   // Output: '000000000000000000000000'

const oneHourAgo = Math.floor(Date.now() / 1000) - 3600           // seconds
db.events.find({ _id: { $gt: ObjectId.createFromTime(oneHourAgo) } }) // events created in the last hour
// Output: all documents inserted within the last hour (uses the _id index)

// Node.js driver: validating user input BEFORE using it as an id
const { ObjectId } = require('mongodb');
function toObjectId(s) {
  if (!ObjectId.isValid(s)) return null;   // note: isValid also accepts any 12-char string, see Tricky Q
  return new ObjectId(s);
}

try {
  new ObjectId('xyz');                      // invalid input throws
} catch (e) {
  console.log(e.name, e.message);
  // Output: BSONError input must be a 24 character hex string, 12 byte Uint8Array, or an integer
}

// A string id does NOT match an ObjectId _id (verified: returns null)
// await col.findOne({ _id: someIdString })               -> null
// await col.findOne({ _id: new ObjectId(someIdString) }) -> the document
```

## 🟠 Express.js / Mongoose Integration

```javascript
const express = require('express');
const mongoose = require('mongoose');
const app = express();

const User = mongoose.model('User', new mongoose.Schema({ name: String }));

app.get('/users/:id', async (req, res) => {
  // Validate FIRST: a bad id would otherwise throw a CastError (500)
  if (!mongoose.isValidObjectId(req.params.id)) {
    return res.status(400).json({ error: 'Invalid id' });
  }
  // Mongoose casts the string to ObjectId automatically in findById
  const user = await User.findById(req.params.id);
  if (!user) return res.status(404).json({ error: 'Not found' });
  // user.id is the string form; user._id is the ObjectId; createdAt can be derived:
  res.json({ id: user.id, createdAt: user._id.getTimestamp() });
});
```

## ⚠️ Common Mistakes to Avoid
❌ Mistake 1: Comparing ObjectIds with `==` / `===` or querying with a string
```javascript
// Wrong - objects compare by reference; string never matches an ObjectId _id
a._id === b._id                              // false even if same value
col.findOne({ _id: req.params.id })          // null

// Right
a._id.equals(b._id)                          // true when same bytes
col.findOne({ _id: new ObjectId(req.params.id) })
```

❌ Mistake 2: Using ObjectId as a secret token or exact creation time
✅ Correct: It is predictable (timestamp + counter) and only has 1-second resolution. Use a crypto-random token for secrets and a real `createdAt` `Date` when precise time is needed.

## 🧠 Tricky Interview Question

**Q: Two documents are inserted in the same second from the same server. Which has the larger `_id`? And can ObjectId collide across servers?**

Answer: The one inserted later: the timestamp ties, the 5-byte random part is identical (same process), and the 3-byte counter is incremented (verified: difference = 1). Across different processes the 5-byte random part differs, so collisions require the same second AND the same random value AND the same counter - practically impossible. Gotcha: ordering is only **approximately** chronological across different servers (their clocks and counters differ within the same second), so never rely on it for strict ordering. Also, `ObjectId.isValid()` can return true for any 12-character string in some driver versions, so validate carefully.

## ⚫ Interview Questions + Answers

Q1: Describe the structure of an ObjectId.
A1: 12 bytes = 4-byte Unix timestamp (seconds) + 5-byte random value per process + 3-byte incrementing counter; displayed as 24 hex characters.

Q2: Who generates the ObjectId, server or client?
A2: The driver (client) generates it before sending the insert; if a document has no `_id`, the server will add one only if the driver did not.

Q3: Why is ObjectId better than auto-increment in distributed systems?
A3: No central coordination, can be generated offline by many nodes, mostly increasing so index inserts are efficient, and not trivially guessable as `1,2,3`.

Q4: How do you get the creation date from an ObjectId?
A4: `id.getTimestamp()` (returns a Date from the first 4 bytes), accurate to the second.

Q5: Can you use something other than ObjectId for `_id`?
A5: Yes: any BSON type except arrays (string, number, UUID, compound object). Choose natural keys (e.g. `orderNumber`) only if unique and immutable.

## 🔷 When to Use + When Not to Use
✅ Use ObjectId when:
- You want zero-config unique ids, multi-server inserts and rough time ordering

❌ Avoid when:
- You need ids that must not leak time/count info (use UUIDv4 or random tokens), or need human-friendly short ids
